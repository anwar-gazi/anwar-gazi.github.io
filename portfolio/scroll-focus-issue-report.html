📋 Executive Summary

This report documents the investigation and resolution of a scroll focus issue in the Kanban board application where touchpad/mouse scroll events intended for overlay components (TaskPane and RunningTasksBar) were incorrectly propagating to the underlying board, causing unintended background scrolling.

Resolution Status: Successfully resolved using scroll event containment via onWheel event handlers and overscrollBehavior: contain CSS property.

🔍 Problem Analysis

Symptoms Observed

  • When TaskPane (modal) was open, scrolling with touchpad would scroll the board behind it
  • When RunningTasksBar (dock) was expanded, scroll events leaked to the board
  • Board's scrollbar remained visible behind overlay components
  • Scroll targeting was inconsistent — users expected overlays to capture scroll events

Root Cause Identification

The issue stemmed from scroll event bubbling in the DOM. When a scrollable container reaches its scroll boundary (top or bottom), the browser propagates remaining scroll delta to ancestor elements. This behavior is called scroll chaining.

Scroll Chain Visualization

→ User scrolls with touchpad over TaskPane
→ TaskPane body scrolls (overflow-y-auto)
→ TaskPane reaches scroll boundary
→ Remaining scroll delta bubbles to parent
→ Board/body scrolls (unintended behavior)

🧪 Approaches Attempted

Approach 1: Body Scroll Lock

Failed

Strategy: Set document.body.style.overflow = "hidden" when overlay opens, restore original value on close.

// Initial implementation
useEffect(() => {
    if (!taskId) return;
    const originalOverflow = document.body.style.overflow;
    document.body.style.overflow = "hidden";
    return () => {
        document.body.style.overflow = originalOverflow;
    };
}, [taskId]);

Problem: When component closed, the original overflow value was sometimes captured as "hidden" (if another component had already set it), causing the board to become permanently non-scrollable.

Approach 2: Reference-Counted Scroll Lock

Partial Success

Strategy: Create a shared utility with lock counter to properly handle nested lock/unlock scenarios.

// src/lib/scrollLock.ts
let lockCount = 0;
let originalOverflow = "";

export function lockBodyScroll() {
    if (lockCount === 0) {
        originalOverflow = document.body.style.overflow;
        document.body.style.overflow = "hidden";
    }
    lockCount++;
}

export function unlockBodyScroll() {
    lockCount--;
    if (lockCount <= 0) {
        lockCount = 0;
        document.body.style.overflow = originalOverflow;
    }
}

Problem: While this fixed the nested lock issue, it still prevented the board from scrolling when the mouse was outside the overlay but the overlay was still open. User requirement was that board should scroll when mouse is over the board, regardless of overlay state.

Approach 3: Event Containment (Final Solution)

Implemented

Strategy: Use onWheel event handlers to stop scroll event propagation combined with overscrollBehavior: contain CSS property.

// TaskPane.tsx - Final implementation
<aside
    style={{ overscrollBehavior: "contain" }}
    onWheel={(e) => e.stopPropagation()}
>
    ...
</aside>

Advantages:

  • No body scroll lock complexity
  • Board remains scrollable when mouse is over it
  • Overlays capture scroll only when mouse is inside them
  • Works correctly on fresh page load
  • No cleanup issues when components unmount

Technical Implementation

The solution combines two complementary techniques:

Technique Purpose Browser Support

💡 Key Learnings

  • Event propagation control is often more precise than global state changes like body overflow
  • overscrollBehavior is a powerful CSS property specifically designed for scroll containment
  • User intent matters: Users expected scroll to work based on mouse position, not overlay state
  • Avoid global DOM modifications when local event handling can achieve the same result
