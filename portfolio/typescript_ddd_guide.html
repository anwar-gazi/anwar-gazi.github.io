1. TypeScript Foundations: Interface vs Type

While often used interchangeably, the distinction between interface and type is critical for library design and error handling performance.

Comparison Matrix

Feature Interface Type Alias
Definition Describes the shape of an object. Creates a new name for any type (object, primitive, union).
Extensibility Extends via extends keyword. Open for declaration merging. Extends via intersection &. Closed to modification.
Declaration Merging ✅ Supported (Crucial for augmenting libraries). ❌ Not Supported (Throws duplicate identifier error).
Computed Properties ❌ Limited support. ✅ Fully supported (Mapped types).
Compiler Performance Faster. Checks cache based on name. Slower. Often recursively evaluates the shape.

Code Implementation

Using Interface

interface User {
  id: string;
  name: string;
}

// Declaration Merging
interface User {
  email: string;
}
// Result: User has id, name, and email

Using Type

type ID = string | number;

type UserStatus = 
  | 'active' 
  | 'suspended';

type User = {
  id: ID;
  status: UserStatus;
}

2. Architectural Strategy: Anemic vs Rich Domain Models

The choice between representing entities as plain data (Anemic) or encapsulated behavior (Rich) dictates the flow of business logic in your application.

PROS
  • Simple Serialization: Objects are already plain JSON.
  • Low Boilerplate: No constructors or accessors needed.
  • Tooling: Works seamlessly with most ORMs (Prisma, TypeORM).
CONS
  • No Invariants: Impossible to prevent invalid states (e.g., a User with no email).
  • Logic Fragmentation: Business rules scatter across Services and Controllers.
  • Low Cohesion: Data is separated from the operations that modify it.

Option B: The Rich Domain Model (DDD)

Entities are defined as class with private state. Logic resides inside the entity. Services simply coordinate workflow.

class Order {
  private status: 'draft' | 'paid' = 'draft';
  private items: OrderItem[] = [];

  public addItem(item: OrderItem): void {
    if (this.status === 'paid') {
      throw new Error("Cannot modify paid order");
    }
    this.items.push(item);
  }
}

The Reconstruction Problem

When fetching data from a database, you receive plain objects. You cannot cast these to a Class. You must reconstitute the entity. 

// user.repository.ts
async findById(id: string): Promise<User> {
  // 1. Get raw data from DB (Plain Object)
  const rawData = await db.users.find({ id });

  // 2. Use Mapper to Reconstitute Domain Entity
  return UserMap.toDomain(rawData);
}

4. Serialization & Data Transfer

Classes do not serialize well by default. They lose methods and private fields may be inaccessible.

The `toJSON` Hook

JavaScript's JSON.stringify() looks for a method named toJSON() on objects being serialized.

class User {
  constructor(private password: string) {}

  toJSON() {
    // Return a plain object literal
    return {
      hidden: "******"
    };
  }
}
Critical Warning: Never expose Domain Entities directly to your API (REST/GraphQL). Doing so couples your external API to your internal domain logic.

The DTO Pattern (Data Transfer Object)

Instead of serializing the Entity directly, convert it to a DTO before sending the response.

5. Final Recommendations

Scenario Recommended Approach
Public Library / API Use Interface (allows merging for consumers).
Complex Business Logic Use Class (Rich Domain Model). Enforce invariants.
Simple CRUD / Microservice Use Interface (Anemic Model). Speed and simplicity.
API Response Type Use Interface or Type (DTOs are data, not behavior).
